# 設計書レビュー

## 🔴 重大な問題（修正必須）

### 1. パスワードの平文保存（5章・10章・15章）

**最も致命的な問題です。**

| 箇所 | 記載内容 | 問題点 |
|---|---|---|
| 5.1 | `password_pt VARCHAR(255) NOT NULL` | カラム名が「平文」を意味する |
| 10章 | 「パスワードは平文保存する」と明記 | 設計方針として明示的に指示 |
| 15章 | 「パスワードが平文保存されている」を完了条件に | **完成判定基準にセキュリティ違反が含まれる** |

これは「設計ミス」ではなく「設計方針の誤り」です。本番環境で運用する以上、**絶対に許容できません**。

**修正案：**
```sql
-- 変更前（×）
password_pt VARCHAR(255) NOT NULL

-- 変更後（○）
password_hash VARCHAR(255) NOT NULL   -- bcrypt/argon2 のハッシュ値
salt      BYTEA                        -- 必要に応じて別途管理
```

- ハッシュアルゴリズムは **bcrypt** または **Argon2id** を推奨
- `password_pt` というカラム名自体が「平文」を連想させるため、`password_hash` に変更すべき
- 15章の完了条件から「平文保存」を削除し、「パスワードハッシュ値として保存されている」に書き換える

### 2. API レスポンスに認証情報が含まれていない（6章）

`POST /api/login` の正常レスポンスが：
```json
{ "message": "ログインしました" }
```
のみでは、**フロントエンドが「ログイン成功した」と判断する方法がありません。**

セッション認証の場合：
- `Set-Cookie: session_id=xxx; HttpOnly; Secure; SameSite=Lax` がレスポンスヘッダーに含まれる必要がある
- フロントエンドは Cookie を自動で送信するため、明示的なトークン受信は不要（ただし、CSRF トークンの取得が必要）

JWT 認証の場合：
```json
{
  "token": "eyJhbGciOi...",
  "expires_in": 3600
}
```
を返す必要があります。

## 🟡 重要な改善点

### 3. パスワード要件が弱すぎる（8章）

| 項目 | 現状 | 推奨 |
|---|---|---|
| 最小文字数 | 8文字 | **12文字以上**（OWASP 2024 基準） |
| 最大文字数 | 128文字 | 問題なし |
| 複雑性要件 | なし | **大文字・小文字・数字・記号の各1種以上** |
| 既知パスワードチェック | なし | HaveIBeenPwned API などとの照合を推奨 |

### 4. CSRF 対策が未記載（10章）

- セッション認証の場合、**CSRF トークン**の発行・検証が必須
- `SameSite=Lax` は防御の一環だが、CSRF トークンと併用すべき
- JWT の場合も、Authorization ヘッダー送信時の CSRF 対策が必要（XSRF-TOKEN Cookie など）

### 5. セッションの有効期限（7章・10章）

- 「セッション作成」の記載はあるが、**有効期限（TTL）** が未定義
- 推奨：`max_age=3600`（1時間）程度で、再認証を促す仕組み
- `Secure` フラグは HTTPS のみ送信されるため必須

### 6. CORS 設定の欠落（2章・6章）

- フロントエンドとバックエンドが別ドメイン/ポートの場合、CORS ヘッダーが必要
- `Access-Control-Allow-Origin`, `Allow-Credentials: true` の記載を推奨

## 🟢 改善提案（中程度）

### 7. 画面遷移図の表現

```text
+----------------+       ログイン成功       +----------------+
|   ログイン      | ----------------------> |     ホーム      |
```

「ログイン成功」の矢印ラベルは、**API レスポンス → フロントエンド判定 → リダイレクト** の3ステップを省略しすぎています。実装時に混乱する可能性があります。

### 8. マイページの `created_at` 表示形式（3.4章）

```text
登録日：2026/09/19
```

- フォーマットが画面ハードコードされている → **国際化（i18n）対応**を視野に入れるべき
- タイムゾーン表記がない（JST? UTC?）→ 明示すべき

### 9. テスト項目の網羅性（13章）

| 不足 | 提案 |
|---|---|
| パスワード要件違反テスト | 7文字、記号なし、既知パスワードなど |
| メール形式不正入力 | `user@`, `.com` など |
| XSS 注入テスト | `<script>alert(1)</script>` をユーザー名に |
| SQLi テスト（API レベル） | `' OR '1'='1` など |
| セッションタイムアウト | 長時間放置後の再アクセス |

### 10. ディレクトリ構成（12章）

- `backend/controllers/auth` のように「auth」が重複している → `controllers/user`, `routes/auth` に分離すべき
- `services/api` がフロントエンドにあるが、**API クライアントの型定義（TypeScript）** をどこに置くか不明確
- 環境変数管理（`.env.example`）の記載がない

## 🔵 小さな指摘

| 箇所 | 内容 |
|---|---|
| 5.1 | `BIGSERIAL` は PostgreSQL 固有。DB 移行を想定するなら `BIGINT + SERIAL` を明示すべき |
| 7章 | 「平文パスワードを比較」と記載 → ハッシュ値の比較に修正が必要（`bcrypt.compare()`） |
| 9章 | 403「権限不足」はログイン機能ではほぼ不要。削除または「管理者のみ」用途として明確化 |
| 15章 | 「HTTPSを前提とした安全な認証処理になっている」→ 平文保存と矛盾するため修正必須 |

## ✅ 良い点

- 画面遷移図が視覚的に分かりやすい
- エラーコードの対応表（9章）が網羅的
- セッション Cookie の属性（HttpOnly, Secure, SameSite）を記載している
- SQL インジェクション対策としてプレースホルダーを明示している
- 「ログイン失敗時にメール存在有無を区別しない」セキュリティ方針が正しい
