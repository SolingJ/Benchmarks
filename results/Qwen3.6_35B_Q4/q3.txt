提示いただいた設計書は、画面遷移・API仕様・テスト項目まで網羅されており、実装に向けた基礎として**構成が非常に明確で良い**です。ただし、**セキュリティ面において重大な誤り**が含まれているため、開発前に必ず修正する必要があります。以下にレビューをまとめます。

## 🔴 重大な修正事項（必須）

### 1. パスワードの平文保存は許容されません
- **該当箇所**: `5.1 usersテーブル`, `10. セキュリティ設計`, `15. 完了条件`
- **問題点**: 現代のWeb開発・セキュリティ基準（OWASP等）において、パスワードを平文でDBに保存することは**重大な脆弱性**です。漏洩時に全ユーザーのアカウントが即座に侵害されます。
- **修正方法**: 
  - DBカラム名を `password_pt` → `password_hash` に変更
  - 登録時・ログイン時に `bcrypt`, `argon2id`, または `scrypt` 等のハッシュ関数を使用
  - 完了条件の「パスワードが平文保存されている」→「パスワードは適切にハッシュ化されて保存されている」へ変更

### 2. 認証方式（セッション vs JWT）が未決定
- **該当箇所**: `2. システム構成`, `7. 認証処理`
- **問題点**: 「セッションまたはJWT」と記載されていますが、両者はセキュリティ要件・実装フローが全く異なります。設計書内で選択せず両方想定すると、CSRF対策やトークン管理で矛盾が生じます。
- **推奨**: 
  - **セッション認証**を選ぶ場合：Cookieに `HttpOnly, Secure, SameSite=Strict/Lax` を設定し、**CSRF対策（SameSite + CSRF Token）**を必須記載にしてください。
  - **JWT認証**を選ぶ場合：トークンを `httpOnly Cookie` に格納するか、`localStorage` に格納してXSS/CSRFのトレードオフを明記してください。Refresh Tokenの仕組みも検討が必要です。

### 3. ログインAPIレスポンスに認証情報が含まれていない
- **該当箇所**: `6.2 ログイン`
- **問題点**: レスポンスが `{ "message": "ログインしました" }` のみでは、フロントエンドが「どうやってログイン状態を保持するか」が不明です。
- **修正例（JWT選択時）**:
  ```json
  {
    "token": "eyJhbGciOiJIUzI1NiIs...",
    "expiresIn": 3600
  }
  ```
  またはセッション利用時は、サーバー側で `Set-Cookie` ヘッダーを返す仕様と明記してください。

## 📝 具体的な修正例（抜粋）

### `5.1 usersテーブル` 修正後
```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL, -- bcrypt/argon2ハッシュ値
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### `7. 認証処理` フロー修正後
```text
1. メールアドレスとパスワードを入力
              ↓
2. POST /api/login
              ↓
3. emailを使用してusersテーブルを検索（プレースホルダー使用）
              ↓
4. ユーザーが存在するか確認
              ↓
5. 入力パスワードをハッシュ化し、DBのpassword_hashと照合
              ↓
6. 認証成功 → セッション/JWT発行 → Cookie/レスポンスに設定
              ↓
7. ホーム画面へ遷移
```

### `10. セキュリティ設計` 追加項目
- **CSRF対策**: セッションCookie利用時は `SameSite=Lax` + CSRF Token検証を必須とする。JWT利用時も `httpOnly Cookie` 格納を推奨し、XSS/CSRFのトレードオフを明記する。
- **レート制限**: 同一IPまたは同一メールアドレスに対し、5分間に10回までログイン試行を制限。超過時は429 Too Many Requestsを返す。
