# レビュー結果

## 結論

この設計書は、**機能範囲や画面遷移としては概ね妥当**です。  
ただし、**セキュリティ設計に重大な欠陥があるため、現行のまま本番実装すべきではありません**。

特に以下が問題です：

- **パスワードを平文で保存していること**
- **セッション／JWTの管理方針が曖昧であること**
- **CSRF対策・レート制限・エラー処理が不十分であること**

このまま実装すると、DBリークや不正ログインなどのリスクが高くなります。  
以下に優先度別に指摘します。

---

# 1. P0：致命的な指摘（本番では不可）

## 1.1 パスワードを平文で保存すべきではない

### 現在の記載

> `password_pt`  
> **平文パスワード**  
> 「パスワードそのものをデータベースへ保存する。」

これは重大なセキュリティ誤りです。

### 問題点

- DBが漏洩した時点で、全ユーザーのパスワードが露出します
- ログ、APIレスポンス、バックアップなどにも平文が残る可能性があります
- 「ログイン成功条件」に「パスワードが平文保存されている」とあるため、設計思想として誤っています

### 推奨修正

パスワードは必ず**ハッシュ化して保存してください**。

例：

- `bcrypt`
- `scrypt`
- `Argon2id`

DBカラムは以下のように変更すべきです。

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX users_email_lower_idx ON users (lower(email));
```

または、PostgreSQLの `CITEXT` を使う場合：

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email CITEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

重要なのは以下です：

- 平文パスワードをDBに保存しない
- APIレスポンスやログにも平文を出さない
- ログイン時は `password_hash` を検証する
- 比較はタイミング安全なライブラリで行う

もし既にプロトタイプで平文保存している場合は、**ユーザー全員に再登録またはパスワード変更を強制し、ハッシュ化に移行する必要があります**。

---

## 1.2 セッション認証／JWT認証の具体策が曖昧

### 現在の記載

> 認証方式：セッション認証 または JWT

これは選択が未定です。  
特にログアウト時の処理が明確になっていません。

### 問題点

- セッションを使う場合、どこに保存するか？
- Cookieで送るのか？
- トークンの有効期限は？
- ログアウト時に破棄する対象は？
- JWTを使う場合、リフレッシュトークンはあるか？
- ログアウトでJWTを無効化できるか？

これらが不明確だと、ログイン状態管理が不安定になります。

### 推奨修正

初期版なら**セッション認証の方がシンプルで安全です**。

#### セッション方式の例

- ログイン成功時：
  - サーバー側セッションストアにセッションIDを保存する
  - CookieにセッションIDを格納する
  - `HttpOnly` / `Secure` / `SameSite=Lax` を設定する

Cookie例：

```text
Set-Cookie: session_id=<crypto-random>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=...
```

さらに以下を明記すべきです：

- セッションIDは暗号学的に乱数生成する
- ログイン時にセッションを作り直す（セッション固定化対策）
- ログアウト時はサーバー側セッションを破棄し、Cookieも削除する
- 複数端末でログインした場合、ログアウトの範囲（現デバイス only / 全デバイス）を明記する

もしJWTを使うなら：

- Access Tokenは短命にする
- Refresh Tokenは `HttpOnly Cookie` で管理する
- ログアウト時にRefresh Tokenを無効化する設計にする
- localStorageにトークンを置かないことを推奨する

# 2. P1：重要（本番前に修正すべき）

## 2.1 CSRF対策が不足している

### 問題点

ログイン、登録、ログアウトはすべて状態を変更するAPIです。  
Cookieの `SameSite` 設定だけでは不十分な場合があります。

### 推奨修正

状態変更系APIには **CSRFトークン** を導入してください。

例：

- サーバーがセッションに CSRF Token を発行する
- フロントエンドからリクエストヘッダーに含める
- バックエンドで検証する

例：

```http
POST /api/login
X-CSRF-Token: xxxxx
```

または、SPAでCookie認証を使う場合は、最低限以下を明確化してください。

- Cookie: `HttpOnly`
- Cookie: `Secure`
- Cookie: `SameSite=Lax` または `Strict`
- 状態変更APIには CSRF Token を併用する

---

## 2.2 レート制限が弱すぎる

### 現在の記載

> 同一IPから5分間に20回まで

これは不十分です。

### 問題点

- IP単体では回避される可能性がある
- 複数IPからの分散攻撃に対応できない
- アカウント単位で連続失敗を抑制していない

### 推奨修正

最低限、以下を組み合わせるべきです。

#### ログインAPI

- IP単位でのレート制限
- メールアドレス／アカウント単位でのレート制限
- 連続失敗時の指数退避またはロックアウト
-一定回数超えたら CAPTCHA を要求する

例：

```text
同一アカウントで5回連続失敗 → 30秒待機
その後60秒、120秒…と増やす
一定回数超えたら15分間ブロック
```

#### 登録API

- IP単位制限
- メールアドレス単位制限
- 大量作成防止のための CAPTCHA も検討する

---

## 2.3 新規登録APIで `password_confirmation` が不足している

### 現在の記載

リクエスト例：

```json
{
  "name": "山田太郎",
  "email": "taro@example.com",
  "password": "Password123!"
}
```

しかし画面設計では「パスワード確認」があります。  
API側でも検証すべきです。

### 推奨修正

登録リクエストは以下のようにすべきです：

```json
{
  "name": "山田太郎",
  "email": "taro@example.com",
  "password": "Password123!",
  "password_confirmation": "Password123!"
}
```

サーバー側で確認してください：

- `password` と `password_confirmation` が一致する
- パスワードポリシーを満たす
- メールアドレスが未登録である
- 入力値の長さ・形式が正しい

エラーレスポンスもフィールド単位を返すのが望ましいです。

例：

```json
{
  "error_code": "VALIDATION_ERROR",
  "message": "入力内容を確認してください",
  "fields": [
    {
      "field": "password",
      "message": "パスワードは8文字以上である必要があります"
    },
    {
      "field": "email",
      "message": "メールアドレス形式が不正です"
    }
  ]
}
```

## 2.4 メールアドレスの一意性は大文字／小文字を区別しないべき

### 問題点

PostgreSQLの `VARCHAR` で `UNIQUE` すると、通常は**大文字・小文字が異なる値**として扱われます。

例：

- `user@example.com`
- `User@Example.com`

これらは実質同じメールアドレスですが、現状では重複しない可能性があります。

### 推奨修正

以下どちらかを採用してください。

#### 方法A：保存前に小文字化して正規化する

```text
email = email.trim().toLowerCase()
```

その後 `UNIQUE` をかける。

#### 方法B：大文字非依存インデックスを作る

```sql
CREATE UNIQUE INDEX users_email_lower_idx ON users (lower(email));
```

#### 方法C：`CITEXT` を使う

```sql
email CITEXT UNIQUE NOT NULL
```

これにより大文字・小文字を区別しない一意性を得られます。

---

## 2.5 パスワードポリシーが弱すぎる

### 現在の記載

> 8文字以上  
> 128文字以下

8文字は本番ではかなり弱いです。

### 推奨修正

最低限、以下を検討してください。

- 10〜12文字以上
- 大文字・小文字・数字・特殊文字の組み合わせ
- 頻出パスワードリストとの照合（できれば）
- ハッシュアルゴリズムと最大長の整合性を取る

特に注意：

- `bcrypt` は **72バイト** までしか使われないため、128文字まで許すなら `Argon2id` や `scrypt` が望ましいです
- `bcrypt` を使う場合は、パスワード長を72以下に制限するのが安全です

---

## 2.6 セキュリティヘッダーが不足している

### 現在の記載

- HTTPS
- Cookie: `HttpOnly`, `Secure`, `SameSite`
- SQLインジェクション対策
- XSS対策

これらは方向性として正しいですが、もう少し具体化すべきです。

### 推奨追加

#### HSTS

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

#### CSP

Content-Security-Policy を設定する。  
特にReact/Next.jsではJSを制御し、外部スクリプト混入を防ぐ。

例：

```http
Content-Security-Policy: default-src 'self'; script-src 'self' ...
```

#### Other headers

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin` など

---

## 2.7 エラー処理は良いが、アカウント存在推測のリスクもある

### 良い点

ログイン失敗時のメッセージ：

```text
メールアドレスまたはパスワードが正しくありません
```

これは適切です。  
「メールが存在しない」「パスワードが違う」を区別しないのは正しい設計です。

### 注意すべき点

登録APIで以下を返す場合、**メールアドレスの存在確認に使られる可能性**があります。

```json
{
  "message": "このメールアドレスは登録されています"
}
```

これはUX上便利な一方、攻撃者が登録済みメールを確認する手段になり得ます。

### 推奨修正

- 登録APIにもレート制限をかける
- 一定回数超えたら CAPTCHA を入れる
- メッセージ設計を慎重にする
- 本番では「重複エラー」の扱いを慎重に検討する

ログインAPIは必ず汎用的な失敗メッセージのままにしてください。

---

## 2.8 タイムゾーン・型が不十分

### 現在の記載

```sql
created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
```

これではタイムゾーン依存になり得ます。

### 推奨修正

`TIMESTAMPTZ` を使用してください。

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

APIレスポンスも ISO 8601 / UTC で返すのが望ましいです。

例：

```json
{
  "created_at": "2026-09-19T09:00:00Z"
}
```

クライアント側で表示時刻に変換します。

---

## 2.9 `updated_at` の扱いを明確にする

初期版ではユーザー情報が更新されないなら、`updated_at` は不要かもしれません。  
ただし残す場合は、いつ更新されるのか明記してください。

例：

- ユーザー名変更時
- メールアドレス変更時
- 管理画面での修正時

もし使わないなら削除してもよいです。

    password_hash TEXT NOT NULL,

    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
