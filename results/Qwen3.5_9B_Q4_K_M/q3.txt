この設計書は、機能要件と画面構成が明確であり、セキュリティへの配慮（HTTPS、SQL 注入防止、エラーメッセージの一般化）も含まれている点で非常に良い基盤となっています。

しかし、**セキュリティ上の致命的な欠陥（平文パスワード保存）** があります。また、認証方式の明確化や開発時の環境設定に関する記述も追記・補強する必要があります。

以下に詳細なレビューを行います。

# レビュー結果

## 1. 致命的な問題（修正必須）

### 1.1 パスワード保存方式
**問題点:**
*   **5.1 users テーブル:** `password_pt`（平文パスワード）と記載されている。
*   **10.2 パスワード:** 「パスワードは平文保存する」と明記されている。
**リスク:**
これは**大規模なセキュリティリスク**です。もしデータベースが漏洩した場合、全てのアカウントのパスワードが盗聴されるため、システムは即座に利用不可能になるか、被害が甚大になります。
**対策:**
パスワードは**必ずハッシュ化**（bcrypt, scrypt, Argon2 など）して保存してください。設計書の記述を以下の通り修正してください。

*   **DB スキーマ:** `password_pt` → `password`（ハッシュ値）
*   **10.2 節:** 「平文保存する」→「ハッシュ化して保存する」
*   **7. 認証処理:** 「5. 平文パスワードを比較」→「5. ハッシュ化パスワードを比較（bcrypt など）」
*   **登録処理:** 入力されたパスワードを DB 保存前にハッシュ化して保存する処理を追加する。

## 2. 推奨される改善（セキュリティ・実装）

### 2.1 認証方式の決定（セッション vs JWT）
**問題点:**
*   **2. システム構成:** 「セッション認証 または JWT」と曖昧に書かれている。
*   **7. 認証処理:** 「セッション作成」とあり、**11. 処理シーケンス**でも Cookie を前提にしているようだが、2 章の「JWT」の記載と矛盾する可能性がある。
**推奨:**
MVP 版では、実装の複雑さを避けるため、**「セッション認証（Cookie）」** あるいは **「JWT（Access Token）」** のどちらか 1 つを決定してください。
*   **Cookie セッション:** ユーザー体験が自然（ブラウザが管理）だが、クロスサイトリクエスト（CSRF）対策が必要。
*   **JWT:** API 指向で、ステートレスだが、トークンの管理と期限管理が必要。
*   **結論:** Web アプリ（React/Next.js）の場合、**HTTP Cookie に Session ID を保存（HttpOnly=True）** するのが、実装の手軽さと CSRF 対策（Next.js の Auth Cookie など）において一般的で安全です。
    *   **2. 認証方式:** 「セッション認証（Cookie）」とする。
    *   **6. ログイン:** リクエストでセッションを Cookie にセットする。

### 2.2 API セキュリティ（CORS / CORS Policy）
**問題点:**
*   API 設計において、フロントエンド（React）とバックエンドが異なるドメインまたはポート（ポート 3000 vs 3001）の場合、**CORS（Cross-Origin Resource Sharing）** が設定されていないと動作しません。また、セキュリティリスクとなります。
**推奨:**
*   **設計書に追加:** 「CORS ポリシーを設定し、許可するオリジン（フロントエンド URL）のみを許可する」と記載する。
*   **10.10 節（Cookie）:** Cookie の `HttpOnly` は必須ですが、**`Secure`**（HTTPS 必須）も厳守してください。

### 2.3 環境変数（Secrets）の管理
**問題点:**
*   DB 接続情報や、セッションの暗号化鍵、JWT の秘密鍵、bcrypt などの塩はコードに書かれていると危険です。
**推奨:**
*   **10. セキュリティ設計**または**12. ディレクトリ構成**に、「環境変数（.env）の管理」**について追記する。
    *   `DATABASE_URL`, `SECRET_KEY`, `NODE_ENV` などの扱いを明記する。

### 2.4 登録直後の動作（UX）
**問題点:**
*   **3.2 新規登録画面:** 「登録成功後はログイン画面へ遷移する」とある。
**推奨:**
ユーザーはパスワードを自分で登録したため、再度入力する必要がありません。
*   **推奨案 1（利便性重視）:** 登録成功後、セッションを即座に発行し、**ホーム画面（/home）** へ自動遷移する。
*   **推奨案 2（分離重視）:** 現在の通りログイン画面へ遷移するが、パスワードを自動入力し、ログインボタンを自動で押す（フォームの自動処理）機能がある場合は、UX 向上になるが、複雑化する。
*   **結論:** MVP では**「自動ログインしてホームへ遷移」**とするのが一般的です。

## 3. 設計の微調整・明確化

### 3.1 データベース設計（5.1 users テーブル）
**現状:**
```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_pt VARCHAR(255) NOT NULL, -- 誤字・脆弱
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```
**修正:**
`password_pt` を `password` へ変更し、`password` の説明に「bcrypt などのアルゴリズムでハッシュ化された値」を明記する。
また、`updated_at` は `ON UPDATE CURRENT_TIMESTAMP` を設定すると、手動更新のロジックが楽になります。

### 3.2 API リクエスト/レスポンス（6.x）
**現状:**
`201 Created` や `409 Conflict` のステータスコードは正しいが、エラーメッセージの構造を統一する。
**追加:**
*   **400 Bad Request:** バリデーションエラー時。
*   **409 Conflict:** メールアドレス重複時。
*   **422 Unprocessable Entity:** 一部のバリデーションエラーで利用する。
*   **レスポンス体:** 詳細なエラーメッセージ（JSON 形式）を返す場合、フロントエンドで容易にハンドリングできる `errors` フィールドを入れると親切です。
    *   例: `{"message": "登録に失敗しました", "errors": {"email": "すでに登録されています"}}`

### 3.3 脆弱性対策の明文化
**現状:**
*   **10.4 率制限:** 「5 分間に 20 回まで」とあるが、**実装場所（Middleware?）** が不明確。
**推奨:**
「ログイン API（`/api/login`）に対して、**ミドルウェア層（または Express の rate-limit など）で IP アドレスベースのレート制限を実装する」**と明記する。
*   **CSRF:** セッション Cookie を使用する場合、CSRF トークン（Next.js なら自動的だが、明示的に記述した方が安全設計として）の必要性に触れるとより堅固になる。

### 3.4 マイページの表示
**現状:**
*   **3.4 マイページ:** 表示項目に「登録日時」があるが、パスワード変更機能やユーザー名変更機能は MVP 外。
**推奨:**
現状の設計は正しいが、「ユーザー情報編集」は MVP 外と明記しているので、**「表示情報のみで、変更は後期バージョンへ」**と再度強調すると、後工程の要件定義に繋がります。
