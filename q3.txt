# ログイン機能付きWebアプリ 設計書

## 1. 概要

### 1.1 目的

ユーザーがメールアドレスとパスワードを使用してログインし、ログイン後の専用画面を利用できるWebアプリケーションを構築する。

### 1.2 対象機能

本アプリでは以下の機能を提供する。

* ユーザー新規登録
* ログイン
* ログアウト
* ログイン状態の保持
* マイページ表示
* ユーザー情報表示

---

## 2. システム構成

以下の3層構成とする。

```text
[ブラウザ]
    ↓ HTTPS
[Webアプリ / APIサーバー]
    ↓
[データベース]
```

構成例：

| 項目      | 使用技術例           |
| ------- | --------------- |
| フロントエンド | React / Next.js |
| バックエンド  | Node.js         |
| API     | REST API        |
| データベース  | PostgreSQL      |
| 認証方式    | セッション認証 または JWT |
| 通信      | HTTPS           |

# 5. データベース設計

## 5.1 usersテーブル

ユーザー情報を管理する。

テーブル名：

```text
users
```

カラム：

| カラム           | 型            | 制約               | 説明            |
| ------------- | ------------ | ---------------- | ------------- |
| id            | BIGINT       | PK               | ユーザーID        |
| name          | VARCHAR(100) | NOT NULL         | ユーザー名         |
| email         | VARCHAR(255) | UNIQUE, NOT NULL | メールアドレス       |
| password_pt   | VARCHAR(255) | NOT NULL         | 平文パスワード |
| created_at    | TIMESTAMP    | NOT NULL         | 登録日時          |
| updated_at    | TIMESTAMP    | NOT NULL         | 更新日時          |

SQL例：

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_pt VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

パスワードそのものをデータベースへ保存する。

# 7. 認証処理

ログイン時の処理フロー：

```text
1. メールアドレスとパスワードを入力
              ↓
2. POST /api/login
              ↓
3. emailを使用してusersテーブルを検索
              ↓
4. ユーザーが存在するか確認
              ↓
5. 平文パスワードを比較
              ↓
6. 認証成功
              ↓
7. セッション作成
              ↓
8. ホーム画面へ遷移
```

認証済みページでは、毎回セッション情報を確認する。

```text
ユーザー
   ↓
GET /home
   ↓
ログイン済み？
   ├─ YES → ホーム表示
   │
   └─ NO  → /loginへリダイレクト
```

# 8. バリデーション

## メールアドレス

以下を確認する。

* 未入力でないこと
* メールアドレス形式であること
* すでに登録されていないこと

例：

```text
user@example.com
```

## パスワード

例として以下の条件を設定する。

* 8文字以上
* 128文字以下

登録画面では、

```text
password
password_confirmation
```

が一致していることも確認する。

# 9. エラー処理

| 状況      | HTTPステータス | 表示内容                     |
| ------- | --------: | ------------------------ |
| 入力値不正   |       400 | 入力内容を確認してください            |
| 認証失敗    |       401 | メールアドレスまたはパスワードが正しくありません |
| 未認証     |       401 | ログインしてください               |
| 権限不足    |       403 | この操作を行う権限がありません          |
| データなし   |       404 | データが見つかりません              |
| メール重複   |       409 | このメールアドレスは登録されています       |
| サーバーエラー |       500 | エラーが発生しました               |

セキュリティ上、ログイン失敗時には、

```text
メールアドレスが存在しません
```

と

```text
パスワードが違います
```

を区別せず、

```text
メールアドレスまたはパスワードが正しくありません
```

と表示する。

# 10. セキュリティ設計

## パスワード

パスワードは平文保存する。

```text
Password123!
      ↓
DBへ保存
```

## HTTPS

本番環境ではすべてHTTPS通信とする。

```text
https://example.com
```

## Cookie

セッションIDをCookieへ保存する場合は、原則として以下を設定する。

```text
HttpOnly
Secure
SameSite
```

## SQLインジェクション対策

SQL文字列を直接連結せず、プレースホルダーまたはORMを利用する。

悪い例：

```text
"SELECT * FROM users WHERE email = '" + email + "'"
```

安全な実装例：

```sql
SELECT *
FROM users
WHERE email = $1;
```

## XSS対策

ユーザーが入力した文字列をHTMLとして直接出力しない。

## ログイン試行対策

短時間に大量のログイン要求が行われた場合に備えて、レート制限を設定する。

例：

```text
同一IPから5分間に20回まで
```

# 13. テスト項目

| No. | テスト内容             | 期待結果        |
| --: | ----------------- | ----------- |
|   1 | 正しい情報でユーザー登録      | 登録できる       |
|   2 | 同じメールアドレスで再登録     | エラーになる      |
|   3 | 正しいメール・パスワードでログイン | ログインできる     |
|   4 | 間違ったパスワードでログイン    | ログインできない    |
|   5 | 存在しないメールでログイン     | ログインできない    |
|   6 | ログイン後にホームへアクセス    | 表示できる       |
|   7 | 未ログインでホームへアクセス    | ログイン画面へ移動   |
|   8 | マイページを表示          | 自分の情報が表示される |
|   9 | ログアウト             | セッションが破棄される |
|  10 | ログアウト後にホームへアクセス   | ログイン画面へ移動   |

# 14. 最小機能一覧

初期バージョンでは以下を実装範囲とする。

```text
ユーザー登録
     ↓
ログイン
     ↓
ホーム
     ↓
マイページ
     ↓
ログアウト
```

パスワード再設定、メール認証、二要素認証、ユーザー情報編集などは初期バージョンの対象外とする。

# 15. 完了条件

以下をすべて満たした状態を完成とする。

* ユーザーを新規登録できる
* 登録済みユーザーがログインできる
* パスワードが平文保存されている
* 未ログインユーザーが認証必須画面へアクセスできない
* ログインユーザーの情報を表示できる
* ログアウトできる
* 基本的な入力エラーが適切に処理される
* HTTPSを前提とした安全な認証処理になっている
